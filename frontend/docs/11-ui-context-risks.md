# 11. UI context risks

## Зачем нужен этот документ

UI-задачи чаще всего ломаются не в коде, а в трактовке контекста.

Нужно проверять не только “что изменить”, но и:

- где именно;
- в каком состоянии;
- для какого пользователя;
- в каком interaction-flow.

## Layout risks

Если пользователь говорит:

- "сюда"
- "рядом"
- "внизу"
- "внутри"

нужно проверить реальную композицию экрана, а не опираться на догадку.

## Read-only и auth-gated states

Если действие в авторизованном режиме работает, а в `readOnly` нет, нужно сохранять parity поведения.

Примеры:

- click открывает auth flow → drop тоже должен открывать auth flow;
- user начал ввод → перед auth flow текст нужно сохранить.

## Draft persistence

Если auth flow может прервать пользовательский ввод:

- текст должен сохраняться заранее;
- восстановление должно быть автоматическим, если это согласовано с задачей;
- scope persistence должен быть явным: только текст, либо текст + media, либо другое.

## Hover и overlay

Если нужен tooltip, dropdown, popover:

- сначала искать shared wrapper;
- не полагаться на `title`, если проект уже использует управляемый tooltip.

## Interaction parity

При добавлении нового способа действия:

- drag-and-drop;
- keyboard shortcut;
- action button;
- retry flow;

нужно проверить, что он не ломает существующие сценарии и не ведет себя тише, чем уже существующий trigger.
