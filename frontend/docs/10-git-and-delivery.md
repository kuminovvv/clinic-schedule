# 10. Git и delivery

## Формат коммитов

Проект использует стандарт [Conventional Commits](https://www.conventionalcommits.org/).

Обязательная форма:

```text
type(scope): описание
```

Где:

- `type` — служебный тип Conventional Commits латиницей: `feat`, `fix`, `refactor`, `test`, `docs`, `chore` и т.д.;
- `scope` — необязательная область изменения в скобках, если она помогает понять impact;
- `описание` — краткое описание изменения на русском языке;
- `!` после `type` или `scope` используется для breaking change по правилам Conventional Commits.

Примеры:

```text
feat(auth): добавить форму входа
fix(cart): исправить дублирование товаров
refactor(shared): вынести типы кнопки
test(features): добавить тесты авторизации
docs(readme): обновить инструкцию по запуску
feat(api)!: изменить формат ответа профиля
```

Дополнительно:

- `type`, optional `scope`, optional `!`, `body` и `footer` должны соответствовать Conventional Commits;
- `subject`, `body` и `footer` пишутся на русском языке, если нет отдельного требования на другой язык;
- нельзя писать subject на английском, если это не оговорено отдельно;
- если commit содержит breaking change, нужно использовать `!` в заголовке и/или footer `BREAKING CHANGE:`;
- commit должен оставаться кратким и предметным: что изменено, а не общий комментарий про работу.

Пример полного сообщения:

```text
feat(composer): добавить сохранение черновика текста

Сохранять текст поста перед переходом в авторизацию
и восстанавливать его после успешного входа.

BREAKING CHANGE: изменён контракт восстановления draft state
```

## Перед commit

Желательно:

```bash
npm run lint
npm test
npm run type-check
```

Если проверка была только точечной, это нужно сказать явно.

## Dirty worktree

Если в рабочем дереве есть чужие изменения:

- не откатывать их;
- не коммитить их без запроса;
- явно отделять свои правки от уже существующих.

## Push hygiene

Перед push проверить:

- что staged только релевантные файлы;
- что branch/remote понятны;
- что локальные посторонние изменения не попали в commit.

## Выгрузка на сервер (Деплой)

Деплой на продакшн-сервер (https://soobota.com) **не запускается** при обычном коммите или пуше в ветку `main`. Текущий frontend pipeline запускается только для Git-тегов формата `v*.*.*`.

Чтобы выгрузить новые изменения на сервер, необходимо выпустить релиз с помощью **Git-тега версии** (`v*.*.*`).

### Технический тег и публичное обновление — разные сущности

Git-тег запускает сборку и может выпускаться для исправления CI, Docker или конфигурации. Такой тег **не добавляется** на страницу «Что нового».

Публичное обновление создается только при наличии заметных для пользователя функций или исправлений. Оно получает стабильный ID по дате, например `2026-08-15`, и может объединять несколько технических тегов.

### Подготовка публичного обновления

При выпуске SemVer-тега GitLab CI автоматически определяет предыдущий тег,
собирает подтверждения из Git и обновляет `/whats-new`. Если защищённая
переменная `DEEPSEEK_API_KEY` доступна, текст готовит DeepSeek; при
недоступности провайдера используется проверяемый fallback на основе
пользовательских `feat`, `fix`, `perf` и `security`-коммитов. Технический релиз
без пользовательских изменений продолжает деплой и не создаёт пустую запись.

Локально команда также автоматически определяет `--id`, `--date`, `--base` и
`--head`:

```bash
pnpm changelog:auto
```

Команда автоматически:

- получает коммиты и изменённые ими файлы только из заданного Git-диапазона;
- просит модель вернуть для каждого пользовательского пункта точные полные хеши коммитов и пути файлов-доказательств;
- отклоняет пункт, если хеш не входит в диапазон, файл не изменялся указанным коммитом или текст содержит запрещённое неподтверждённое обещание;
- сохраняет проверяемый audit trail в игнорируемый `src/shared/data/changelog-draft.json`;
- сразу обновляет публичный `src/shared/data/changelog.json` без ручного редактирования `verification`.
- перед CI-генерацией объединяет данные с опубликованным
  `https://soobota.com/whats-new.json`, поэтому записи предыдущих релизов не
  теряются между tag pipelines.
- сохраняет уже подготовленную и проверенную запись с тем же ID, поэтому
  повторный pipeline не перезаписывает отредактированный текст.

Параметры `--id`, `--date`, `--base` и `--head` остаются доступны для
повторной генерации нестандартного диапазона.

Если модель не находит пользовательских изменений или не может привязать пункт к реальному коммиту и его файлу, публичное обновление не создаётся. Технический деплой при этом можно продолжить отдельно.

Фактическое значение ключа нельзя добавлять в исходники, `.env.example`, аргументы коммита или changelog. Для проверки смысла изменений генератор передаёт внешнему API названия коммитов, пути файлов и Git diff, поэтому его нельзя запускать для конфиденциального диапазона. Слишком большой диапазон отклоняется — в таком случае выберите более близкий `--base`.

Для диагностики можно остановиться после создания автоматически проверенного черновика:

```bash
pnpm changelog:draft -- --id 2026-08-15 --base v1.2.34 --head HEAD
pnpm changelog:publish
```

Это запасной двухшаговый режим; ручное заполнение `verification` не требуется. Перед commit запустите:

```bash
pnpm changelog:validate
pnpm test:changelog
```

Закоммитьте только публичный `changelog.json` вместе с относящимися к релизу изменениями. Черновик и ключ в Git не добавляются.

Если в диапазоне нет пользовательских изменений, публичный changelog пропускается, а технический деплой продолжается обычным способом.

### Пошаговый флоу технического релиза

1. **Создание тега версии**:
   Создайте локально Git-тег, соответствующий новой версии (например, `v0.2.0`):
   ```bash
   git tag v0.2.0
   ```

2. **Пуш тега на сервер**:
   Отправьте созданный тег в GitLab. Это действие автоматически запустит сборку и деплой на прод-сервер:
   ```bash
   git push origin v0.2.0
   ```

3. **Контроль сборки**:
   Перейдите в интерфейс GitLab в раздел **CI/CD -> Pipelines** и убедитесь, что пайплайн для тега `v0.2.0` успешно завершился (`success`).
